# Freight Dispatch: handoff notes

A Factorio **2.1** mod (`freight-dispatch/`) that replaces the factory game with a railway tycoon game. It was written from scratch with the user, Steve, over many play-and-fix rounds. Read this before changing anything.

## Goal and the user

- Steve loves **laying track, rail signals and chain signals, and watching trains run**. The mod's purpose is a game loop built around designing a train network instead of a factory. Every feature should push toward "more trains on shared track, so signalling matters".
- It was inspired by the abandoned mod NSkelin/Transportorio (0.17/0.18 era, unusable on 2.x). None of its code is used.
- Steve plays the game and reports what he sees in-game ("mail won't unload", "inventory full of people"). He likes a clear explanation of *why* something happened, then a fix. He is fine with fixes landing as new mod versions.
- **He wants a chill game** (said explicitly at v0.2.0). He hones a few small networks (his "Greenfield loop" with a hub-and-spoke goods system, and the "Fairbridge loop") rather than expanding fast. So: **no** mechanics that push expansion (subsidies for unconnected sites were proposed and put on hold), **no** ongoing costs or upkeep ("Factorio vanilla doesn't have that"), **no** decline of unserved sites. He likes contracts for routes he already runs ("it's a relief"), and he likes progression and seeing multipliers.
- Environment: Windows 11, Steam Factorio **2.1.25 (since 2026-11-27; was 2.1.24), base game only (no Space Age, so no elevated rails, quality or planets)** at `D:\SteamLibrary\steamapps\common\Factorio`. Other enabled mods: `flib`, `EditorExtensions`. Saves are named like `2026-11-07 Freight Dispatch Mod N.zip` in `%APPDATA%\Factorio\saves`.

## Workflow

1. Edit `freight-dispatch/` in this folder (this is the source of truth).
2. Bump `version` in `freight-dispatch/info.json` on every change.
3. Test headlessly: `.\tools\fd.ps1 test` (fresh map plus harness) or `.\tools\fd.ps1 save` (a copy of the user's newest save plus the inspector).
4. Install: `.\tools\fd.ps1 install`, which copies to `%APPDATA%\Factorio\mods\freight-dispatch` as an unzipped folder.
5. Tell the user to **fully restart Factorio**. Mods only load at startup, and loading a save after an update shows a harmless mod-version-changed notice.

Run the script as `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\fd.ps1 <mode>`, because the default execution policy blocks unsigned scripts. `save` mode assumes the user's mod set is base + flib + EditorExtensions; update the mod-list line in `fd.ps1` if that changes. On a healthy `test` run, `money` jumps by about $20k or more per trip after the first few minutes and `ghostvalid=false`.

`tools/fd.ps1` runs factorio.exe with its own `--config` and `write-data` folder (`%TEMP%\fd-work`). This is required because the user usually has the game open, and sharing the normal write-data folder fails with **"Couldn't create lock file"**. The full log is `%TEMP%\fd-work\data\factorio-current.log`. `FDDUMP` blocks are multi-line (`serpent.block`), so read that file rather than relying on the script's line filter.

### What headless testing can and cannot verify

- **Can:** prototype loading, `on_init`, map and site generation, train service (loading, unloading, pay), refuel, contracts, ghost revive through the `queue_ghost` remote, and anything in a copy of the user's save (including flipping their train to automatic, or checking their character's inventory through `game.players`).
- **Cannot:** anything needing a connected player or a renderer. That includes all GUI clicks, `cursor_ghost`, remote-view camera moves (`goto_site`), player-placed ghosts (`on_built_entity` with `player_index`), deconstruction and upgrade planner events, and **map charting**: `force.chart()` does nothing in `--benchmark`, so `is_chunk_charted` stays false even at spawn. Be explicit with the user about which of these are untested.
- `runtime-api.json` for the exact installed version is at `D:\SteamLibrary\steamapps\common\Factorio\doc-html\runtime-api.json`. Query it with `ConvertFrom-Json` instead of guessing at 2.1 API changes.

## Game design (as built)

**Passenger and mail scale (0.9.8, Steve: "Millgate, population 4,386, has 19,670 passengers waiting"):** every passenger and mail quantity is now in units of `C.TOWN_SCALE` (10) old ones. Towns make pop / `PAX_PER_POP` / 10 passengers and pop / 400 / 10 mail per second, the waiting cap is (STOCK_CAP + 4·pop) / 10, stack size is 5 (a 120-slot wagon holds 600), fares are ×10 (rates 30 and 35), each unit costs 10 units of loading budget (so wagons fill at the old pace), Spaceport colonists/mail are 400..1,200 / 200..600, and town-cargo contract amounts are ÷10 (rounded to 10). Figures elsewhere in this file from before 0.9.8 (waiting counts, rocket colonists, interrupt thresholds) are in the old scale. `rescale_town_cargo()` migrates an old save once (`storage.town_scale`; new maps set it in `on_init`): town stock, every wagon stack (Factorio keeps oversized 50-stacks when the stack size drops, so each stack is divided in place, keeping slot filters) and its lots, pad colonists/mail, contracts and flow meters, then prints a chat note. Verified on a copy of his "2026-11-26 07" save: wagons 194,904 → 19,410, waiting 245k → 24.5k (towns about 2,000 each); with his item-count interrupt thresholds also ÷10, passenger and mail fares over 15 min were within 2 to 5% of 0.9.5. Without that, his pad interrupts ("mail-17 > 500") stop firing and pad mail piles up aboard (fares −15 to −20%), so he must divide them by 10.

- **World:** `on_init` (new game only) creates surface `freight` from nauvis settings, with resource and enemy autoplace `size = 0`, sparse trees, no cliffs, peaceful mode and always day. Players are teleported there and freeplay's crash site, intro and starting items are disabled. Research is disabled, and all recipes are disabled *except* shop items. Those stay "unlocked" so their ghosts can be placed; they still can't be crafted because no materials exist.
- **Sites:** towns, coal mines, iron mines, lumber camps, steel mills, factories and power plants. Each has a catchment ring (towns start at 22 tiles, others 18; read it through `site_radius(site)`, never `C.KINDS[kind].radius`). **Since 0.4.0** (Steve wanted fewer, more interesting sites, spread further apart): 8 starter sites form a full goods chain (2 towns, coal, iron, forest, steel mill, factory, power plant) within about 560 tiles of spawn (400 before 0.7.2), and the whole `C.STARTERS` layout is rotated by a random angle per map. Spacing (`spot_ok`): `SITE_MIN_DIST` 250 between any sites and `TOWN_MIN_DIST` 420 between towns (0.7.2, Steve wanted more spread again, everything ×1.4 for his new game; 0.4.0 had 180 / 300, and before that 100 for all, and his 0.3.x save packed 190 sites at a median of 114 tiles). Sites are **no longer rolled per generated chunk** (the old 10%-per-chunk queue is gone). Instead `maybe_found_site` (every 2 s, at most once per `FOUND_GAP` 30 s) founds one site whenever `room_for_site()`. **Kind (0.4.6, Steve asked: his save had spare iron, steel and factories but no lumber to connect):** `urgent_kind` walks `C.FOUND_TIERS` (coal + lumber; iron + power plant; town (0.4.7, Steve said towns felt scarce); steel; factory) and picks the first kind with no *unserved* site. The first three tiers are `basic` and are founded even when the spare cap is full, so the pool can exceed the cap by at most 5. With no gap, it's a kind missing from the map, or else a weighted pick (town weight 18, was 32) that avoids kinds already unserved. The `served` remote returns per-kind served/spare counts and the urgent kind. It's placed 280 to 700 tiles (0.7.2; was 200 to 500) from a random served site (or spawn) on generated dry land, with its 3×3 chunk footprint generated first (ungenerated land is requested and retried), and announced in chat with a gps link. Sites are charted and chart-tagged.
- **A stop serves a site** if it sits within the ring (`linked_sites`, cached in `storage.stop_links`, and the cache is cleared whenever a site is created). New stops are auto-renamed after their site once, at build time. The user may rename them afterwards, and duplicate names are intended (multi-platform stations).
- **Destinations (0.9.0, Steve's design; old saves are not supported, he said that's fine):** every town (up to `C.DEST_TOWNS` 16; founding skips towns once all 16 numbers are used) and Spaceport (`C.DEST_PADS` 4, numbers 17 to 20) gets `site.no` (`storage.dest_sites[n] = site id`, assigned in `create_site`). Passengers and mail bound there are separate items `fd-passengers-N` / `fd-mail-N` (data.lua: disc tinted `C.DEST_COLORS[n]` + vanilla picture + number; locale "Passengers to N", "Colonists to Spaceport N"). `C.BASE[item]` / `C.base()` map a destination item back to its cargo, and `C.CARGO` has an entry per destination item (same rate and decay). Site stock, flow meters, contracts, `earned_item` and Spaceport counts all use the base cargo; only wagons hold destination items. **Destinations are picked as cargo boards** (Steve: "simply get on and trust the train"), never while waiting: `train_dests(train)` (cached 10 s in `storage.dest_cache`) collects numbered sites linked to stops named in the train's schedule records and interrupt targets; a target containing `[virtual-signal=signal-item-parameter]` (item wildcard) is expanded per destination item, and the stop must be in that site's ring. Every candidate stop is checked with `game.train_manager.request_train_path{type="all-goals-accessible"}`, so separate networks never trade riders. `boarding_dests` weights towns by pop (min 100) and a Spaceport at twice the average town weight while `pad_room` > 0, nothing within `MIN_DIST`; `split_by_weight` divides each load. Unload takes only the destination item of the site's own number. Riders whose destination the train no longer serves get off at the next town into its generic stock with a flying text (no pay). Stops: the first stop built in a numbered site is named `[item=fd-passengers-N] unload` (0.9.1; 0.9.0 used "stop"), the next one `[item=fd-mail-N] unload` while the site has a passenger stop and no mail stop (checked by name and ring, so a destroyed stop doesn't count), others passengers again, so the 2.x dispatch interrupt "item count [wildcard] > 0 -> [wildcard] unload" works. `site_title` appends the passenger icon of the number. No transfers or hubs yet (Steve: keep it simple).
- **Wagon filters (0.9.0, narrowed in 0.9.1 at Steve's request):** `extend_wagon_filters(inv, old)` runs only when `apply_wagon_capacity` grows a wagon, and only if every old slot was filtered to one cargo; the new slots get that filter (the exact one if all old slots share it, else the plain cargo, since `wagon_insert` switches slots between destinations). Filters are never changed otherwise. `wagon_insert` lets a slot filtered to any passenger item take any destination: it switches empty same-cargo slots' filters to the item being loaded.
- **Train service:**
  - **Arrival:** service runs **instantly** in `on_train_changed_state` on arrival (before the engine checks wait conditions), then once per second while the train is waiting.
  - **Unload:** instant, with no rate limit. Every cargo *lot* whose origin is at least `MIN_DIST` (60) tiles from the site and is accepted there comes off and is paid. Lots still near their origin **stay aboard**. Untracked surplus (more items than records) is dumped for free. **Back-pressure (0.3.4, Steve asked for vanilla-like behaviour):** at steel mills and factories, only what fits in the input pile (`INPUT_CAP` 20,000 per item) comes off. The rest stays aboard and unloads on later seconds as the pile shrinks, so an "Empty cargo" train waits like a vanilla train at full chests. The status line notes a full pile. (A chat message was tried and removed at Steve's request: waiting is normal Factorio, so don't nag.) Towns have no pile and take everything, so town passenger and mail handling is unchanged. Power plants (0.4.1) take only what fits in their fuel pile, the same way. Before 0.3.4 the overflow was paid and then discarded. Steve's train 93 (Birchmouth coal to Elmbridge, which never gets ore) will park at Elmbridge under the new rule.
  - **Load:** `load_rate()` (the Station crews upgrade: 400/600/900/1,400) per wagon per second, **shared evenly between every produced cargo type waiting there**, so passengers can't starve mail.
  - **Drop-off stops:** if the train's *current schedule record* has an **"Empty cargo"** wait condition, the stop is drop-off only. Nothing loads there, and cargo that originated at this site goes back into its stock.
- **Pay** = amount × cargo rate × distance (straight line, origin site to destination site) / 100 × time factor. The time factor is 1 within a grace period of 20 s + distance/12, then decays linearly over the cargo's `decay` seconds, with a floor of 0.25.
- **Production:**
  - **Primary industries** produce `base × (1 + LEVEL_BONUS·(level−1)) × (0.6 + 0.4·rating)` per second (0.3.0: base coal/ore 12, wood 10, `LEVEL_BONUS` 1.0, `LEVEL_AT` ×2.5; before that 5/5/4 and 0.5, so a level-5 mine made only 15/s and starved the chain), with stock capped at `STOCK_CAP × level`. `rating` rises when anything is picked up each minute. Level-ups happen at shipped totals in `LEVEL_AT`.
  - **Towns** produce passengers at pop/`PAX_PER_POP` (120 since 0.6.0, was 60) and mail at pop/400 per second, and **grow only from goods** (0.3.0, Steve's choice): each new resident costs `M.goods_per_resident` = `GOODS_PER_RESIDENT` (100) × max(1, pop/1000)^`GROWTH_EXP` (1.5) goods (0.6.0; 0.3.0 to 0.5.x was 50 × pop/1000, linear). A town needs about 216k goods to reach 2,000 pop, 613k for 3,000 and 2.2M for 5,000. Without goods a town is stable (never declines). The design loop: passengers and mail are steady income that funds the factory chain, and goods grow cities. History: up to 0.2.1, passengers, mail and plain service all grew towns, compounding about 1%/min. Steve's save reached 96k-pop towns, $45k/s income and $254M lifetime in 8.3 h, with passengers about 75% of income, mail 25% and freight negligible. 0.2.2 tried a sqrt slowdown (`growth_damp`), and 0.3.0 replaced it. Towns add buildings as they grow (pop/120 + 2, max 64) on an 8×8 slot grid at offsets ±5/9/13/17, which leaves a 7-tile clear "railway street" cross through the centre. Every free slot is retried each minute, and a slot is skipped while any player-force entity is within 2.5 tiles, so buildings never box in track. The ring grows (never shrinks) to the outermost building + 12 tiles (`update_ring`, which also clears `stop_links`). Steve asked for this because the old solid grid filled a fixed 22-tile ring. 0.1.9's `relayout_towns` migration rebuilt old towns (any town without `site.built`).
  - **Secondary industries** (`KINDS[k].main/booster/base_yield/full_yield`) process up to `PROCESS_RATE` (50, was 25) × level of the main input per second. Cargo rates (0.3.0): steel 3.0 (was 2), goods 5.0 (was 3). Yield goes linearly from `base_yield` to `full_yield` as the booster covers ½ unit per main unit. The booster alone makes nothing. The steel mill is ore with a coal booster (0.5 → 1). The factory is steel with a lumber booster (1 → 2); before 0.2.0 lumber alone made goods, but Steve's factories were steel-only, so nothing was nerfed.
  - **Site text** (0.4.3, Steve asked for consistency): every site has the title, then `M.site_status` (inventory only: `Level N` or `Pop N` · `In:` piles with limits, e.g. `[ore] 0 / 20,000` · `Out:` with limits (towns without) · `Accepts` icons for towns and plants; plants show `Fuel: X / 18,000 (full, 20 min)`), then `M.site_detail` (a third render text at y−8, also in the Sites list): one state ("Producing", "Making X from Y", "Idle: needs [item]", "Paused: output full", "Stockpile full: waiting for pickup", "Stable"/"Growing", "Running: powering N sites"/"Out of fuel"), multipliers in one format and order `(level x2, boost x1.5, power x1.25, service x0.70)`, then `Next level N%`. Service is hidden at 0.95 or above, and level x1 is hidden. Separator `  ·  ` (Steve's choice). Teaching sentences ("Coal only boosts it", "lumber counts half", "Ship it out to restart") were removed on purpose; the Help explains those. Secondary industries store `site.used` (main input per second) for the "from" figure.
- **Power plants** (0.4.1, Steve asked for a reason to supply them; `C.POWER`, `update_power` at the start of `simulate_second`): they accept coal (fuel value 1) and lumber (0.5) into `site.fuel` (cap 18,000, which is 20 min), burn 15/s, and count up `site.burnt`, which drives their levels through `LEVEL_AT`. While fuel > 0, every other site within `supply_radius` (350 + 35 per level since 0.7.2, scaled with the spacing; was 250 + 25) gets `site.powered_by` = the nearest running plant (no stacking; `site.powering` counts them). `power_mult` (×1.25, Steve chose subtle) applies to town passengers and mail, `goods_per_resident` (÷1.25), primary output and secondary processing. Running dry just removes the bonus. Each plant draws a supply circle in game and chart mode (`update_supply_circle`, alpha 0.75 and width 12 / 6 and opaque since 0.8.1 (Steve asked twice: too subtle; 0.5.3 had 0.75 and 6 / 3), dimmed when dry; 0.9.7 also a filled disc in chart mode, premultiplied alpha 0.16 (0.05 dry), because line widths don't grow as the map zooms out, and the map outline went 6 → 10). Detail lines: plant fuel, sites powered and level; other sites get "Powered by X: +25%". Site signals add `signal-F` = fuel. Founding places a power plant at the best of 40 candidates by the count of sites no plant covers yet (served ones count double). Design intent: radius-limited, so one hub can't power the map; more plants means more fuel trains.
- **Economy:** you start with $300k. Contracts (up to 3 at a time, 30 min deadline) give a bonus for delivering X units of item to a site, counting **any** train's *paid* deliveries. Since 0.4.2 there is never more than one active contract per site and cargo, and each delivered unit counts once (oldest matching contract first, up to what it still needs). Before that, duplicates could appear and one delivery counted toward both. They only target **served** sites (a stop in the ring, `served_ids()`), for cargo some served site produces, and pairs already delivered (`site.recv`) are 4× as likely. Freight (anything not in `C.TOWN_CARGO`) is a further 3× as likely, has double the amount, and pays amount × rate × 12 (town cargo: × 6), but **since 0.7.8 at least `C.CONTRACT_INCOME_MINS` (3) minutes of `M.recent_income_per_min()`** (the last 10-minute `income_log` interval), rounded to $10k, because flat rewards had become under a minute of income (on his save they jumped from about $1.5M to $7M to $10M). Only with nothing served can they name any site.
- **0.6.0 rebalance** (Steve, after a 10.9 h game: $234M lifetime, goods 56% of income from one level-5 factory, towns at 4,800 to 5,600 pop with 60k to 90k passengers waiting, top upgrades only near the end, and slow early income while he worked out track layouts): goods rate 5.0 → 3.5, passengers 1.5 → 3.0 at half the volume (pop/120), mail 2.5 → 3.5, the steeper growth cost above, starter towns 700/550 → 1,000/800, and top upgrade tiers Express $30M → $12M, Jumbo $40M → $15M, Automated $20M → $8M, Rocket boots $10M → $4M. Estimated late-game mix on his network: goods ~45%, passengers + mail ~25%, steel and raw ~30%, about 15% less late income. `storage.earned_item[item]` counts lifetime pay per cargo, and every 10 min `storage.income_log` gets {tick, lifetime, pop, earned} (remote `income_log`), so the next playthrough's income curve can be read from the save. fd-debug logs `FDINCOME` every 2 min.
- **Spaceport** (0.7.0, Steve's end game; `C.SPACEPORT`, kind `spaceport`, building `fd-spaceport-silo` since 0.7.4 = a deep copy of the vanilla `rocket-silo` with a void energy source, no modules, not minable/operable, placed on force neutral. Each second `update_spaceport` sets `rocket_parts` to the paid fraction (while `building_rocket`; at 100% the engine plays lights, doors opening and the rocket rising to `rocket_ready`), and once the cargo is aboard and the status is `rocket_ready` it calls `silo.launch_rocket()` and then `launch_rocket(site, silo)`. Steve asked for the real door/rocket animation: before 0.7.4 it was the simple-entity `fd-silo` (silo picture, doors shut) with sprite `fd-rocket` drawn on top and moved up, which is still the fallback when no silo exists. `on_configuration_changed` (`ensure_pad_silo`) swaps the old picture for the real silo. `no_silo_victory()` calls `silo_script.set_no_victory` on init, config change and before each launch, or freeplay would show the "you won" screen. Verified on a copy of his save: the whole status sequence, launch counted at `launch_starting`, doors close and the next rocket's parts climb; not seen with a renderer). **0.7.8 (Steve asked):** (a) **several Spaceports.** The first stays free at the last rank; after that the Shop and the Spaceport window sell more (`M.buy_pad`, prices `buy_prices` $25M/$50M/$100M and then doubling; `storage.pads_bought`, `storage.pads_pending`, one pending at a time). `maybe_found_site` founds them with `found_site("spaceport")`, and `spot_ok` keeps `pad_min_dist` (700) tiles between pads. `M.spaceports()` lists them in id order; `M.spaceport()` is still the first (`storage.spaceport_id`, never overwritten by later pads). Each pad has its own `site.pad`, level and launches; satellites, the reserve and the pause checkbox are shared. The Spaceport window stacks every pad in a scroll pane. Remotes `spaceports` and `buy_pad`; `set_pad(t, id)`. (b) **Satellites no longer raise fares.** `sat_mult()` (1% per launch, up to +50%, which takes 50 launches) multiplies town passenger and mail production and `supply_radius`. On his save, income fell from about $3.6M/min to $3.2M/min at 11 launches. Verified on a copy of his save: the bought pad was founded about 2,900 tiles from the first, the price moved to $50M, satellites ran x1.11 to x1.14, and contract rewards came out at $6.7M to $9.6M. The Shop row, the window and buttons are untested (they need a player). **0.7.7 launch when loaded** (Steve, after 11 launches: his interrupt trains filled the pad with 5 of the 10 min still to go, so logistics made no difference): cash is paid only up to `cost × pad_cargo_frac` (the average share of colonists, mail and goods aboard) and at most `cost / build_secs` per second, with `build_secs` now 3 min, so a rocket launches as soon as it is loaded and paid. Levels became 4,000/2,000/24k/$4M, 6,000/3,000/36k/$5M, 8,000/4,000/48k/$6M, 10,000/5,000/60k/$7M, 12,000/6,000/72k/$8M; `update_spaceport` refunds an old save's `paid` above the new cost. On a copy of his save (level 3, one 12k goods train to the pad), rockets came every 4 to 5 min instead of 10, with goods the limit. The figures below are from before 0.7.7. Reaching the last rank sets `storage.pad_wanted` (as does `on_configuration_changed` for a save already there), and `maybe_found_site` then founds exactly one (`found_site("spaceport")`, outside the cap and `FOUND_GAP`; `storage.spaceport_id`). It isn't in `KIND_ORDER`, `KIND_WEIGHTS` or `FOUND_TIERS`, and contracts never name it. A rocket needs colonists (`fd-passengers`), mail and (0.7.1) goods delivered by train (normal fares; unload takes only `pad_room`, the rest stays aboard like a full pile) plus cash, paid every second over `build_secs` (10 min since 0.7.1, was 15) and never below the reserve the player picks in the Spaceport window (`storage.pad_reserve` index into `reserves`, default $2M; `storage.pad_paused` from the checkbox). It launches when all three are done (`launch_rocket`: chat, a rising sprite moved by `on_nth_tick(2)` `animate_launches`), and the next one starts at once. `sites[id]` = {kind, name, x, y, level, shipped, delivered, picked_min, rating, stock, input, pop, building_count, built (set of TOWN_SLOTS indices), radius (towns, grown ring), render, tagged} · `stop_links[stop_unit] = {site ids}` · `wagons[wagon_unit][item] = { {amount, ox, oy, tick, site}, ... }` (the lot list; `get_lots()` migrates the old 0.1.0 single-record format) · `waiting[train_id] = LuaTrain` · `stuck` · `ghost_queue` · `next_found_tick`, `found_kind` (founding) · `contracts` · `money`, `lifetime`, `income_hist`, `rank` · `seed` (own deterministic LCG; never `math.random` after init) · `disabled` (dormant flag) · `throttle` (message rate limiting).

Wagon records are cleaned up through `script.register_on_object_destroyed` → `on_object_destroyed.useful_id`.

## Key decisions and why

- **Dormant in existing saves.** Factorio enables new mods globally. If `on_init` sees `game.tick > 0` (mod added to an old factory save), it sets `storage.disabled`, unregisters every handler (also in `on_load`) and prints a notice. Without this, loading any old save would teleport the player and wipe its research and recipes.
- **Per-origin cargo lots, not one averaged origin.** The 0.1.0 averaged origin drifted when mixed loads accumulated, until cargo "came from" its own destination and jammed the train forever.
- **"Empty cargo" = drop-off.** Steve's schedules naturally use "Empty" at destinations. Loading there meant the train could never empty and would sit forever filling with locals. A more general rule ("cargo back home gets off free") was tried and caused load-then-unload churn every second at towns, which both produce and accept passengers. Don't reintroduce it.
- **Instant unload on arrival.** Otherwise "Full cargo" is already true when a full train arrives, and it leaves without unloading.
- **Fair-share loading.** First-come loading let ~3,700 waiting passengers take all capacity, so mail contracts were impossible.
- **Ghosts over items.** Steve called instant ghost building, charged in cash, a "huge QOL" win. Keep inventory-first, then cash.
- **No power and no radars** in this game, so visibility comes from trains, stops and paid surveys.

## Pitfalls already hit (2.1 API and engine)

- Lowering an item's `stack_size` leaves existing larger stacks in inventories as they are (they're over-full, not split or deleted), so any rescale has to fix the counts itself.
- **Every new prototype needs a name in `locale/en/locale.cfg`** (`[entity-name]` and `[item-name]`), or the game shows `Unknown key: "entity-name.…"`. Headless tests don't catch this. Missed for `fd-spaceport-silo` (0.7.4), Plasma/Antimatter fuel (0.8.2) and `fd-arithmetic` (0.8.3); fixed in 0.8.4.
- `LuaEntity.active` write was **removed in 2.1**. Use `disabled_by_script`. Check the 2.1 changelog (`data/changelog.txt`, the top ~1,300 lines) for other removals: recipe `category` became `categories`, crafting inventory defines were renamed, and `fluidbox` was removed.
- Map-gen autoplace `frequency = 0` → **NaN noise-expression crash** in `create_surface`. Set `size = 0` only.
- `ghost.revive()` at a position where the real entity can't exist (e.g. a signal overlapping the rail) **returns quietly and leaves the ghost**. In tests, use `can_place_entity` first.
- Straight rails are 2×2. Script-created ones at even x snap to odd centres. Train stops sit ±2 tiles beside the rail; find the offset by checking `stop.connected_rail`.
- Schedules: use `train.get_schedule()` (LuaSchedule: `current`, `get_record{schedule_index=}`, `add_record`). `train.schedule =` may also still work.
- `game.train_manager.get_trains{surface=}` is the 2.x way to list trains.
- **GPS rich text `[gps=x,y,surface]` is only clickable in chat**, not in mod GUI labels, which is why navigation uses real buttons.
- Lua can't define GUI styles at runtime. Stick to known vanilla style names (`frame_title`, `draggable_space_header`, `frame_action_button`, `inside_shallow_frame_with_padding`). `mini_button_aligned_to_text_vertically` was removed for being uncertain.
- The simulation clamps stock with `min(cap, stock + x)`, so stock returned above the cap is trimmed on the next tick. That's acceptable.
- Cargo icons reuse vanilla pictures (wood, coal, iron ore, steel plate, blueprint for mail, iron chest for goods). In 0.3.1 Steve set a stop condition on vanilla **Wood** instead of `fd-wood`, so it never fired. Since 0.3.2 every `fd-*` cargo icon has a small locomotive badge, and since 0.3.3 mail uses its own envelope picture (`graphics/mail.png`, drawn with System.Drawing) (bottom right), and the Help says to pick the freight version. Earlier he also read a mail contract as "deliver 1500 blueprint", which is why contract text includes the cargo name.
- `train_state` numbers seen in logs: 0 = on_the_path, 5 = arrive_station, 6 = wait_station, 8 = manual_control (a train in manual mode is never serviced).
- Rail signal `close_signal` + condition: the signal is **closed while the condition is true** (`signal_state` 3 = reserved_by_circuit_network). A train stop with `circuit_enable_disable` is enabled while its condition is true. Both verified headlessly in fd-test. `is_shortcut_available` errors for vanilla shortcuts.
- Constant combinator filters need `quality = "normal"` on **every** signal, virtual ones included. Without it the filter is stored and reads back fine, but nothing is output. Until 0.4.8, `[F]`/`[L]`/`[P]` from Site signals silently never reached the wire.
- A combinator output connector has no circuit network until something is wired to it, so `get_circuit_network(combinator_output_*)` returns nil. The 2.1 decider supports `else_outputs`.
- Locomotives default to `copy_color_from_train_stop = true`, and stops default to red (0.95, 0, 0), so every train turns red at each stop. Each new carriage also forms a one-carriage train (`on_train_created`) before it couples, so painting is deferred to the next second through `storage.paint_queue`.

- **Interrupt wildcards:** the item wildcard (`signal-item-parameter`) is only bound by "item count" conditions and takes the first item that passes, in item order (for destinations: the lowest number). In a circuit condition it never fires, even next to an item-count condition. Circuit conditions need the **signal wildcard** (`signal-signal-parameter`), which binds to a signal sent to the train by its stop ("Send to train"), and a `[virtual-signal=signal-signal-parameter] unload` target becomes `[item=fd-passengers-N] unload`. `train_dests` expands both wildcards (`PARAMS`); before 0.9.3 riders on a signal-wildcard train were put off as unserved. Verified in fd-test. Also: circuit wire reach between stops and combinators is about 9 to 10 tiles, and `connect_to` returns false beyond it.

## Gameplay tips the user has been given (keep the Help text consistent)

- Pick-up stops: "Full cargo OR 30 seconds". Drop-off-only stops: "Empty cargo". Two-way passenger lines and loops: "Full cargo OR 30 s" (or "Inactivity 5 s OR 30 s") at every town.
- Loops (A → B → C → A) work for passengers and mail because they're accepted by any town at least 60 tiles from their origin. Freight is directional.
- Don't tear down idle trains (no upkeep). Train groups, multiple platforms sharing a stop name, and 2.0 wildcard interrupts are all usable.
